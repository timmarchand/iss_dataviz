Shapefiles

Shapefiles are special types of data that include information about geography, such as points (latitude, longitude), paths (a bunch of connected latitudes and longitudes) and areas (a bunch of connected latitudes and longitudes that form a complete shape). Nowadays, most government agencies provide shapefiles for their jurisdictions. For global mapping data, you can use the Natural Earth project:

  • Natural Earth
  • GADM — administrative boundaries for every country, down to municipality level
  • GSI (Geospatial Information Authority of Japan / 国土地理院)
  • e-Stat 国土数値情報 — official Japanese boundary and statistical map data
  • National Land Numerical Information (国土数値情報ダウンロードサービス)

The good news for us: most of what we need for Japan and East Asia comes bundled in R packages, so we rarely have to download and unzip a single .shp file by hand. We’ll lean on {rnaturalearth} for that.

Projections and coordinate reference systems

As you read in this week’s readings, projections matter a lot for maps. You can convert your geographic data between different coordinate systems (or projections) fairly easily with {sf}. You can use coord_sf(crs = st_crs("XXXX")) to convert coordinate reference systems (CRS) as you plot, or use st_transform() to convert data frames to a different CRS.

NoteNot 100% correct

TECHNICALLY coordinate systems and projection systems are different things, but this is not a geography course, so we don’t have to care that much about the nuance.

There are standard indexes of more than 4,000 of these projections (!!!) at epsg.io.

Super important: When using these projections, you need to specify both the projection catalog (ESRI or EPSG; see here for the difference) and the projection number, separated by a colon (e.g. “ESRI:54030”). Fortunately epsg.io makes this super easy: go to the epsg.io page for the projection you want to use and the page title will have the correct name.

Here are some common ones for world maps:

  • ESRI:54002: Equidistant cylindrical projection for the world1
  • EPSG:3395: Mercator projection for the world
  • ESRI:54008: Sinusoidal projection for the world
  • ESRI:54009: Mollweide projection for the world
  • ESRI:54030: Robinson projection for the world (This is my favorite world projection.)
  • EPSG:4326: WGS 84: DOD GPS coordinates (standard −180 to 180 system)

And here are some that are tuned specifically for Japan and East Asia. Just as the US has projections built for North America (NAD83) or even for one single state, Japan has its own national geodetic datum and a set of local plane-rectangular zones:

  • EPSG:6668: JGD2011 — the modern Japanese geodetic datum (latitude/longitude)
  • EPSG:6677: JGD2011 / Japan Plane Rectangular CS IX — the zone covering Tokyo and the Kantō region
  • EPSG:4612: JGD2000 — the previous national datum, still common in older data
  • EPSG:30169: Old Tokyo datum, Japan Plane Rectangular CS IX (handy for seeing why datums get revised)
  • ESRI:102025: Albers equal-area for Asia North, good for whole-region East Asia maps

Alternatively, instead of using these index numbers, you can use any of the names listed here, such as:

  • "+proj=merc": Mercator
  • "+proj=robin": Robinson
  • "+proj=moll": Mollweide
  • "+proj=aeqd": Azimuthal Equidistant

Basic plotting

If you look at the world_map dataset in RStudio, you’ll see it’s just a standard data frame, where the last column is the magical geometry column with the latitude/longitude details for the borders of every country. RStudio only shows you 50 columns at a time in the RStudio viewer, so you’ll need to move to the next page of columns with the » button in the top left corner.

Because this is just a data frame, we can do all our normal dplyr things to it. Let’s get rid of Antarctica, since it takes up a big proportion of the southern hemisphere:

Code 
world_sans_antarctica <- world_map |>
  filter(name != "Antarctica")

Ready to plot a map? Here’s all you need to do:

Code 
ggplot() +
  geom_sf(data = world_sans_antarctica)

If you couldn’t tell from the lecture, I’m completely blown away by how amazingly easy this is every time I plot a map :)

Because this is a regular ggplot geom, all our regular aesthetics and themes and everything work:

Code 
ggplot() +

          fill = "#669438", color = "#32481B", linewidth = 0.25) +
  theme_void()

Zooming in on East Asia

A world map is a fine starting point, but for this class most of us live in (or come from) East Asia, so let’s zoom in. We don’t need a separate file for this — we can keep the same world data and just restrict the plotting window with coord_sf(). The xlim and ylim arguments take longitude and latitude bounds:

Code 
ggplot() +
  geom_sf(data = world_sans_antarctica,
          fill = "#669438", color = "white", linewidth = 0.25) +
  coord_sf(xlim = c(95, 150), ylim = c(20, 50)) +  # East Asia window
  theme_void()

That gives us China, the Korean peninsula, Japan, and Taiwan in one frame. We can also fill each country a different colour so the borders pop. Let’s filter down to just the East Asian countries and fill by name:

Code 
east_asia <- world_sans_antarctica |>
  filter(name %in% c("Japan", "China", "South Korea",
                     "North Korea", "Taiwan", "Mongolia"))

ggplot() +
  geom_sf(data = east_asia, aes(fill = name), color = "white", linewidth = 0.3) +
  scale_fill_viridis_d(option = "plasma") +
  labs(fill = NULL) +
  coord_sf(crs = st_crs("ESRI:102025")) +  # Albers equal-area for Asia
  theme_void()
NoteCountry names in Natural Earth

The name column uses common English names, so it’s "South Korea" rather than "Republic of Korea". If a filter() ever comes back empty, the quickest fix is to run world_sans_antarctica |> filter(continent == "Asia") |> pull(name) and copy the exact spelling.

Repositioning far-flung islands

Japan has the same problem the US does with Alaska and Hawaii: Okinawa (沖縄県) sits hundreds of kilometres southwest of the main islands, so a faithful map leaves a huge empty ocean in the middle and shrinks everything else. The usual fix is to move the distant part closer for display — a deliberate cartographic white lie that we signal with an inset box.

The US approach with {tigris}

For US maps there’s a purpose-built tool. The {tigris} package provides a neat interface to the US Census’s TIGER shapefiles, and its shift_geometry() function automatically relocates Alaska, Hawaii, and Puerto Rico so they tuck in below the lower 48. It does all the projection and coordinate maths for you:

Code 
if (!requireNamespace("tigris", quietly = TRUE)) install.packages("tigris")
library(tigris)
options(tigris_use_cache = TRUE)

# Grab state boundaries straight from the Census
us_states <- states(cb = TRUE, resolution = "20m", progress_bar = FALSE)

us_states_shifted <- us_states |>
  shift_geometry()  # Move AK, HI, and PR into view

ggplot() +
  geom_sf(data = us_states_shifted) +
  coord_sf(crs = st_crs("ESRI:102003")) +  # Albers
  theme_void()

shift_geometry() has an optional position argument ("below" by default, or "outside" to place the territories roughly where they sit in real life). The catch: it only works on US data, because the shift distances are hard-coded for Alaska, Hawaii, and Puerto Rico. There’s no country = "Japan" switch.

The Japan approach with {jpmap}

For Japan, the closest equivalent is the {jpmap} package, which ships prefecture geometry plus a layout_japan() function that repositions Okinawa automatically — even across facets. Like rnaturalearthhires, it’s a GitHub-only package, so we guard the install the same way:

Code 
if (!requireNamespace("jpmap", quietly = TRUE)) {
  if (!requireNamespace("remotes", quietly = TRUE)) install.packages("remotes")
  remotes::install_github("UchidaMizuki/jpmap")
}
Code 
library(jpmap)

# jpmap::prefecture is an sf object with all 47 prefectures
base_map <- ggplot(jpmap::prefecture) +
  geom_sf(fill = "#A5D46A", color = "white", linewidth = 0.2) +
  theme_void()

# layout_japan() returns a relaid-out plot with Okinawa moved into the inset
layout_japan(base_map)

Doing it by hand

layout_japan() is convenient, but it hides what’s actually happening, and it only works with {jpmap}’s own geometry — not the japan_prefectures data we already have from rnaturalearth. Since these are just sf data frames, we can do the shift ourselves, which is worth seeing once because it works on any shapefile, for any country.

The idea is exactly what shift_geometry() does internally: pull the far-flung piece out, add an offset to every coordinate in its geometry to slide it where we want, then stack it back on. We’ll work in plain lat/long degrees (EPSG:4326), so the offset reads as “move this many degrees east and north.” We want to tuck Okinawa into the empty Sea of Japan, northwest of the main islands — that’s a move both west and well north, into open water that sits clear of Honshū’s coast and the Noto Peninsula. About +5° longitude and +14° latitude drops it neatly into that gap:

Code 
# Separate the mainland from Okinawa
japan_main <- japan_prefectures |>
  filter(!str_detect(str_to_lower(name), "okinawa"))

okinawa <- japan_prefectures |>
  filter(str_detect(str_to_lower(name), "okinawa"))

# How far to slide Okinawa: northwest, into the Sea of Japan.
offset <- c(5, 14)  # c(longitude, latitude) in degrees

# Slide every coordinate in Okinawa's geometry. Adding a numeric vector to a
# geometry shifts it, but it STRIPS the CRS, so we re-attach it immediately.
okinawa_shifted <- okinawa
st_geometry(okinawa_shifted) <- st_geometry(okinawa) + offset
st_crs(okinawa_shifted) <- st_crs(okinawa)

# Recombine into one dataset
japan_shifted <- bind_rows(japan_main, okinawa_shifted)
WarningRe-attach the CRS!

The line st_geometry(x) + offset does raw coordinate arithmetic, and R can’t know the offset was meant to be in degrees, so it drops the coordinate reference system. If you forget the st_crs(okinawa_shifted) <- st_crs(okinawa) line, the next coord_sf() will either error or silently misplace Okinawa. This is the single most common mistake with manual shifting.

Now we plot the recombined map, and draw a box around the relocated Okinawa to make clear it’s been moved — the same honesty the original Alaska/Hawaii maps owe their readers. One catch: we want the box drawn in the same coordinate space as the map. If we used annotate("rect", ...) with raw numbers, it would be drawn in the projected (metre-based) space and land in the wrong place once coord_sf() reprojects everything. The reliable way is to build the box as a real sf polygon from the shifted Okinawa’s own bounding box, so geom_sf() reprojects it along with the rest:

Code 
# Build an inset box from the shifted prefecture's own extent, with a little padding
okinawa_box <- okinawa_shifted |>
  st_bbox() |>
  st_as_sfc() |>           # bbox -> polygon
  st_buffer(0.4)           # pad the edges slightly (degrees)

ggplot() +
  geom_sf(data = japan_shifted, fill = "#A5D46A", color = "white",
          linewidth = 0.2) +
  geom_sf(data = okinawa_box, fill = NA, color = "grey50", linewidth = 0.3) +
  coord_sf(crs = st_crs("EPSG:6668")) +
  theme_void()

The same trick works on any data sitting in Okinawa — a shapefile of Okinawan airports, say. Apply the identical + offset to those points and they’ll travel along with the prefecture into the inset.

Making your own geocoded data

Plotting boundary shapefiles with geom_sf() is magical because {sf} deals with all the projection issues for us. But lots of data doesn’t come as shapefiles. Often you just have two columns of latitude and longitude stored as plain numbers, and geom_sf() can’t use those directly — it needs that magical geometry column.

Fortunately, if we have latitude and longitude information, we can build our own geometry column.

Let’s say we want to mark some cities on our map of Japan. We can make a mini dataset with tribble(). I found these points from Google Maps: right click anywhere in Google Maps, select “What’s here?”, and you’ll see the exact coordinates for that spot.

Code 
japan_cities <- tribble(
  ~city,       ~lat,      ~long,
  "Tokyo",     35.689487, 139.691711,
  "Osaka",     34.693738, 135.502165,
  "Sapporo",   43.062096, 141.354376,
  "Fukuoka",   33.590355, 130.401716
)

This is just a normal dataset, and the lat and long columns are just numbers. R doesn’t know that those are actually geographic coordinates. We convert them to the magic geometry column with st_as_sf(). We have to define two things: which columns are the longitude and latitude, and what CRS the coordinates use. Google Maps uses EPSG:4326, the GPS system, so we specify that:

Code 
japan_cities_geometry <- japan_cities |>
  st_as_sf(coords = c("long", "lat"), crs = st_crs("EPSG:4326"))

The longitude and latitude columns are gone, replaced by a single geometry column, which means we can plot it with geom_sf():

Code 
ggplot() +
  geom_sf(data = japan_prefectures, fill = "#EC8E55", color = "white",
          linewidth = 0.2) +
  geom_sf(data = japan_cities_geometry, size = 3) +
  coord_sf(crs = st_crs("EPSG:6668")) +
  theme_void()

We can use geom_sf_label() (or geom_sf_text()) to add labels in the correct locations too. It will give you a warning, but you can ignore it — it’s just complaining that positioning might not be 100% accurate because of the globe-flattening problem.

Code 
ggplot() +
  geom_sf(data = japan_prefectures, fill = "#EC8E55", color = "white",
          linewidth = 0.2) +
  geom_sf(data = japan_cities_geometry, size = 3) +
  geom_sf_label(data = japan_cities_geometry, aes(label = city),
                nudge_y = 0.15) +
  coord_sf(crs = st_crs("EPSG:6668")) +
  theme_void()

Nudging labels off their points

A single nudge_y shoves every label the same direction, which often isn’t what you want — a label might end up in the sea for one city and on top of a neighbour for another. You can pass a vector instead, one value per city, to move each label its own direction. The order has to match the order of the rows in the data:

Code 
ggplot() +
  geom_sf(data = japan_prefectures, fill = "#EC8E55", color = "white",
          linewidth = 0.2) +
  geom_sf(data = japan_cities_geometry, size = 3) +
  geom_sf_text(data = japan_cities_geometry, aes(label = city),
               # Tokyo, Osaka, Sapporo, Fukuoka — one offset each
               nudge_x = c(-0.7, -0.7,  0.9, -0.8),
               nudge_y = c( 0.3, -0.3,  0.0, -0.3)) +
  coord_sf(crs = st_crs("EPSG:6668")) +
  theme_void()

That works, but hand-tuning offsets gets tedious fast and breaks the moment you add another city.

Letting {ggrepel} do it automatically

The general solution is the {ggrepel} package, which automatically pushes labels away from their points and away from each other, drawing a thin leader line back to each marker. Because ggrepel predates {sf} and doesn’t read geometry columns on its own, the trick is to feed it aes(geometry = geometry) together with stat = "sf_coordinates", which extracts the point coordinates for it:

Code 
library(ggrepel)

ggplot() +
  geom_sf(data = japan_prefectures, fill = "#EC8E55", color = "white",
          linewidth = 0.2) +
  geom_sf(data = japan_cities_geometry, size = 3) +
  geom_text_repel(data = japan_cities_geometry,
                  aes(label = city, geometry = geometry),
                  stat = "sf_coordinates",
                  size = 4,
                  min.segment.length = 0,  # always draw the leader line
                  box.padding = 0.3) +     # how hard to push labels apart
  coord_sf(crs = st_crs("EPSG:6668")) +
  theme_void()

For four well-spaced cities ggrepel is mild overkill, but it’s exactly the tool you’ll want the moment labels start colliding — add a fifth and sixth city and the manual nudge approach falls apart while this one keeps coping. Use geom_label_repel() instead of geom_text_repel() if you want each label in its own little box.

Automatic geocoding by address

Using st_as_sf() is neat when you already have latitude and longitude, but what if you have a list of addresses instead? It’s easy enough to right click on Google Maps, but you don’t want to do that hundreds of times for large-scale data.

Fortunately there are online geocoding services that return GIS data for addresses you feed them. The easiest way to use them is the {tidygeocoder} package, which connects to lots of free and paid services (run ?geo for full details). Some common methods:

  • "osm": OpenStreetMap via Nominatim. FREE, and works worldwide — including Japanese addresses.
  • "arcgis": ArcGIS. FREE and paid; also global.
  • "google": Google. Needs an API key in "GOOGLEGEOCODE_API_KEY".
ImportantThe US Census geocoder is US-only

The original version of this example used method = "census", but the US Census service only covers the United States — it has no idea where Gakushuin University is. For Japan (or anywhere outside the US), use "osm" instead. This is a good habit anyway, since "osm" works globally.

Let’s make a little dataset of places around Tokyo to geocode:

NoteClipping vs. windowing

There are two ways to “zoom” a map, and they’re not the same. coord_sf(xlim = ..., ylim = ...) is windowing — it keeps all the data but only shows part of it, like cropping a photo. st_intersection() is clipping — it actually removes the geometry outside the box, changing the underlying data. Use windowing for a quick visual zoom; use clipping when you genuinely want to drop the far-flung pieces (like Tokyo’s islands) so later calculations or layers don’t drag them back in.

Plotting point data from a file: universities in Tokyo

Shapefiles aren’t limited to lines and areas — they can also be collections of points, and points are often what you actually want to map (every school, every station, every café). You don’t have to hand-type coordinates into a tribble() either; lots of point data is freely available to download.

A great free source is OpenStreetMap (OSM), the “Wikipedia of maps.” Everything in OSM is tagged with simple key=value labels — a university is tagged amenity=university, a café is amenity=cafe, a station is railway=station, and so on. We can ask OSM for every feature carrying a particular tag inside a particular area and download the result.

Querying OSM with Overpass Turbo

The tool for this is Overpass Turbo, a web front-end to the OSM database. You write a short query in the Overpass QL language, run it, and export the matching features as a GeoJSON file — a text-based geographic format that {sf} reads natively.

Here’s the query for every university in the Tokyo 23 special wards. Paste it into the box at overpass-turbo.eu and click Run:

[out:json][timeout:60];
// Define the search area: Tokyo Metropolis (admin_level 4)
area["name"="東京都"]["admin_level"="4"]->.tokyo;
// Find universities of all geometry types inside that area
(
  node["amenity"="university"](area.tokyo);
  way["amenity"="university"](area.tokyo);
  relation["amenity"="university"](area.tokyo);
);
out center;

Let’s read that line by line, because the structure is reusable for almost any OSM query:

  • [out:json][timeout:60]; — settings: return JSON, and give up after 60 seconds.
  • area["name"="東京都"]["admin_level"="4"]->.tokyo; — find the administrative area named 東京都 (Tokyo Metropolis) and store it in a variable called .tokyo. admin_level=4 is the prefecture level in Japan.
  • The block in parentheses collects three things inside that area: nodes (single points, like a small campus pinned to one spot), ways (buildings or campus outlines drawn as shapes), and relations (complex multi-part features). A university might be tagged as any of these, so we ask for all three.
  • out center; — output the results, and for the ways and relations that are really shapes, return a single centre point instead of the full polygon. That’s what keeps everything as tidy points rather than a mix of dots and blobs.
TipAdapting the query

Want every café in Tokyo instead? Change amenity=university to amenity=cafe. Want hospitals in Osaka? Change the area name to 大阪府 and the tag to amenity=hospital. The skeleton stays identical. The OSM wiki’s map features page lists all the tags.

Once it runs, click Export → download/copy as GeoJSON and save the file into your project as data/tokyo_universities.geojson.

There’s a catch that comes up constantly with OSM data: one university often appears as several points. A big institution like the University of Tokyo is tagged once for its Hongō campus, once for Komaba, sometimes again for individual faculties — so a raw count badly overstates how many universities there are, and our later join would attach the same enrolment figure to each duplicate.

For a clean map we want one dot per institution, but OSM doesn’t give us that. A single university shows up many times — separate campuses, individual faculties, even named buildings — each as its own point with a slightly different name_en. ## Shapefiles

Shapefiles are special types of data that include information about geography, such as points (latitude, longitude), paths (a bunch of connected latitudes and longitudes) and areas (a bunch of connected latitudes and longitudes that form a complete shape). Nowadays, most government agencies provide shapefiles for their jurisdictions. For global mapping data, you can use the Natural Earth project:

- [Natural Earth](https://www.naturalearthdata.com/)
- [GADM](https://gadm.org/) — administrative boundaries for every country, down to municipality level
- [GSI (Geospatial Information Authority of Japan / 国土地理院)](https://www.gsi.go.jp/)
- [e-Stat 国土数値情報](https://www.e-stat.go.jp/gis) — official Japanese boundary and statistical map data
- [National Land Numerical Information (国土数値情報ダウンロードサービス)](https://nlftp.mlit.go.jp/ksj/)

The good news for us: most of what we need for Japan and East Asia comes bundled in R packages, so we rarely have to download and unzip a single `.shp` file by hand. We'll lean on `{rnaturalearth}` for that.

## Projections and coordinate reference systems

As you read in this week's readings, projections matter a lot for maps. You can convert your geographic data between different coordinate systems (or projections) fairly easily with `{sf}`. You can use `coord_sf(crs = st_crs("XXXX"))` to convert coordinate reference systems (CRS) as you plot, or use `st_transform()` to convert data frames to a different CRS.

::: {.callout-note}
### Not 100% correct

TECHNICALLY coordinate systems and projection systems [are different things](https://gis.stackexchange.com/a/149751/56265), but this is not a geography course, so we don't have to care that much about the nuance.
:::

There are standard indexes of more than 4,000 of these projections (!!!) at [epsg.io](https://epsg.io/).

**Super important**: When using these projections, you need to specify both the projection catalog (ESRI or EPSG; [see here for the difference](https://gis.stackexchange.com/a/169211/56265)) and the projection number, separated by a colon (e.g. "`ESRI:54030`"). Fortunately [epsg.io](http://epsg.io/) makes this super easy: go to the epsg.io page for the projection you want to use and the page title will have the correct name.

Here are some common ones for world maps:

- [ESRI:54002](http://epsg.io/54002): Equidistant cylindrical projection for the world[^gall-peters]
- [EPSG:3395](http://epsg.io/3395): Mercator projection for the world
- [ESRI:54008](http://epsg.io/54008): Sinusoidal projection for the world
- [ESRI:54009](http://epsg.io/54009): Mollweide projection for the world
- [ESRI:54030](http://epsg.io/54030): Robinson projection for the world (This is my favorite world projection.)
- [EPSG:4326](http://epsg.io/4326): WGS 84: DOD GPS coordinates (standard −180 to 180 system)

And here are some that are tuned specifically for Japan and East Asia. Just as the US has projections built for North America (NAD83) or even for one single state, Japan has its own national geodetic datum and a set of local plane-rectangular zones:

- [EPSG:6668](https://epsg.io/6668): JGD2011 — the modern Japanese geodetic datum (latitude/longitude)
- [EPSG:6677](https://epsg.io/6677): JGD2011 / Japan Plane Rectangular CS IX — the zone covering **Tokyo** and the Kantō region
- [EPSG:4612](https://epsg.io/4612): JGD2000 — the previous national datum, still common in older data
- [EPSG:30169](https://epsg.io/30169): Old Tokyo datum, Japan Plane Rectangular CS IX (handy for seeing *why* datums get revised)
- [ESRI:102025](https://epsg.io/102025): Albers equal-area for Asia North, good for whole-region East Asia maps

[^gall-peters]: This is essentially the [Gall-Peters projection](https://en.wikipedia.org/wiki/Gall%E2%80%93Peters_projection) from [the West Wing clip](https://www.youtube.com/watch?v=vVX-PrBRtTY).

Alternatively, instead of using these index numbers, you can use any of the names listed [here](https://proj.org/operations/projections/index.html), such as:

- `"+proj=merc"`: Mercator
- `"+proj=robin"`: Robinson
- `"+proj=moll"`: Mollweide
- `"+proj=aeqd"`: Azimuthal Equidistant

## Repositioning far-flung islands

Japan has the same problem the US does with Alaska and Hawaii: Okinawa (沖縄県) sits hundreds of kilometres southwest of the main islands, so a faithful map leaves a huge empty ocean in the middle and shrinks everything else. The usual fix is to *move* the distant part closer for display — a deliberate cartographic white lie that we signal with an inset box.

### The US approach with {tigris}

For US maps there's a purpose-built tool. The [`{tigris}`](https://github.com/walkerke/tigris) package provides a neat interface to the US Census's TIGER shapefiles, and its `shift_geometry()` function automatically relocates Alaska, Hawaii, and Puerto Rico so they tuck in below the lower 48. It does all the projection and coordinate maths for you:

```{r tigris-shifting, warning=FALSE, message=FALSE}
if (!requireNamespace("tigris", quietly = TRUE)) install.packages("tigris")
library(tigris)
options(tigris_use_cache = TRUE)

# Grab state boundaries straight from the Census
us_states <- states(cb = TRUE, resolution = "20m", progress_bar = FALSE)

us_states_shifted <- us_states |>
  shift_geometry()  # Move AK, HI, and PR into view

ggplot() +
  geom_sf(data = us_states_shifted) +
  coord_sf(crs = st_crs("ESRI:102003")) +  # Albers
  theme_void()
```

`shift_geometry()` has an optional `position` argument (`"below"` by default, or `"outside"` to place the territories roughly where they sit in real life). The catch: it *only* works on US data, because the shift distances are hard-coded for Alaska, Hawaii, and Puerto Rico. There's no `country = "Japan"` switch.

### The Japan approach with {jpmap}

For Japan, the closest equivalent is the [`{jpmap}`](https://github.com/UchidaMizuki/jpmap) package, which ships prefecture geometry plus a `layout_japan()` function that repositions Okinawa automatically — even across facets. Like `rnaturalearthhires`, it's a GitHub-only package, so we guard the install the same way:

```{r jpmap-install, message=FALSE, warning=FALSE}

  if (!requireNamespace("remotes", quietly = TRUE)) install.packages("remotes")
  remotes::install_github("UchidaMizuki/jpmap")
}
```

```{r jpmap-layout, warning=FALSE, message=FALSE, fig.width=7, fig.height=7}

base_map <- ggplot(jpmap::prefecture) +
  geom_sf(fill = "#A5D46A", color = "white", linewidth = 0.2) +
  theme_void()

# layout_japan() returns a relaid-out plot with Okinawa moved into the inset

```

### Doing it by hand

`layout_japan()` is convenient, but it hides what's actually happening, and it only works with `{jpmap}`'s own geometry — not the `japan_prefectures` data we already have from `rnaturalearth`. Since these are just `sf` data frames, we can do the shift ourselves, which is worth seeing once because it works on *any* shapefile, for *any* country.

The idea is exactly what `shift_geometry()` does internally: pull the far-flung piece out, add an offset to every coordinate in its geometry to slide it where we want, then stack it back on. We'll work in plain lat/long degrees (EPSG:4326), so the offset reads as "move this many degrees east and north." We want to tuck Okinawa into the empty **Sea of Japan**, northwest of the main islands — that's a move both west and well north, into open water that sits clear of Honshū's coast and the Noto Peninsula. About +5° longitude and +14° latitude drops it neatly into that gap:

```{r okinawa-shift}
# Separate the mainland from Okinawa
japan_main <- japan_prefectures |>
  filter(!str_detect(str_to_lower(name), "okinawa"))

okinawa <- japan_prefectures |>
  filter(str_detect(str_to_lower(name), "okinawa"))

# How far to slide Okinawa: northwest, into the Sea of Japan.
offset <- c(5, 14)  # c(longitude, latitude) in degrees

# Slide every coordinate in Okinawa's geometry. Adding a numeric vector to a
# geometry shifts it, but it STRIPS the CRS, so we re-attach it immediately.
okinawa_shifted <- okinawa
st_geometry(okinawa_shifted) <- st_geometry(okinawa) + offset
st_crs(okinawa_shifted) <- st_crs(okinawa)

# Recombine into one dataset
japan_shifted <- bind_rows(japan_main, okinawa_shifted)
```

::: {.callout-warning}
### Re-attach the CRS!

The line `st_geometry(x) + offset` does raw coordinate arithmetic, and R can't know the offset was meant to be in degrees, so it drops the coordinate reference system. If you forget the `st_crs(okinawa_shifted) <- st_crs(okinawa)` line, the next `coord_sf()` will either error or silently misplace Okinawa. This is the single most common mistake with manual shifting.
:::

Now we plot the recombined map, and draw a box around the relocated Okinawa to make clear it's been moved — the same honesty the original Alaska/Hawaii maps owe their readers. One catch: we want the box drawn in the *same* coordinate space as the map. If we used `annotate("rect", ...)` with raw numbers, it would be drawn in the projected (metre-based) space and land in the wrong place once `coord_sf()` reprojects everything. The reliable way is to build the box as a real `sf` polygon from the shifted Okinawa's own bounding box, so `geom_sf()` reprojects it along with the rest:

```{r okinawa-shift-plot, fig.width=8, fig.height=8}
# Build an inset box from the shifted prefecture's own extent, with a little padding
okinawa_box <- okinawa_shifted |>
  st_bbox() |>
  st_as_sfc() |>           # bbox -> polygon
  st_buffer(0.4)           # pad the edges slightly (degrees)

ggplot() +
  geom_sf(data = japan_shifted, fill = "#A5D46A", color = "white",
          linewidth = 0.2) +
  geom_sf(data = okinawa_box, fill = NA, color = "grey50", linewidth = 0.3) +
  coord_sf(crs = st_crs("EPSG:6668")) +
  theme_void()
```

The same trick works on any data sitting in Okinawa — a shapefile of Okinawan airports, say. Apply the identical `+ offset` to those points and they'll travel along with the prefecture into the inset.

## Making your own geocoded data

Plotting boundary shapefiles with `geom_sf()` is magical because `{sf}` deals with all the projection issues for us. But lots of data *doesn't* come as shapefiles. Often you just have two columns of latitude and longitude stored as plain numbers, and `geom_sf()` can't use those directly — it needs that magical `geometry` column.

Fortunately, if we have latitude and longitude information, we can build our own `geometry` column.

Let's say we want to mark some cities on our map of Japan. We can make a mini dataset with `tribble()`. I found these points from Google Maps: right click anywhere in Google Maps, select "What's here?", and you'll see the exact coordinates for that spot.

```{r japan-cities}
japan_cities <- tribble(
  ~city,       ~lat,      ~long,
  "Tokyo",     35.689487, 139.691711,
  "Osaka",     34.693738, 135.502165,
  "Sapporo",   43.062096, 141.354376,
  "Fukuoka",   33.590355, 130.401716
)
japan_cities
```

This is just a normal dataset, and the `lat` and `long` columns are just numbers. R doesn't know that those are actually geographic coordinates. We convert them to the magic `geometry` column with `st_as_sf()`. We have to define two things: which columns are the longitude and latitude, and what CRS the coordinates use. Google Maps uses [EPSG:4326, the GPS system](http://epsg.io/4326), so we specify that:

```{r japan-cities-convert}
japan_cities_geometry <- japan_cities |>
  st_as_sf(coords = c("long", "lat"), crs = st_crs("EPSG:4326"))
japan_cities_geometry
```

The longitude and latitude columns are gone, replaced by a single `geometry` column, which means we can plot it with `geom_sf()`:

```{r japan-with-cities}
ggplot() +
  geom_sf(data = japan_prefectures, fill = "#EC8E55", color = "white",
          linewidth = 0.2) +
  geom_sf(data = japan_cities_geometry, size = 3) +
  coord_sf(crs = st_crs("EPSG:6668")) +
  theme_void()
```

We can use `geom_sf_label()` (or `geom_sf_text()`) to add labels in the correct locations too. It will give you a warning, but you can ignore it — it's just complaining that positioning might not be 100% accurate because of the globe-flattening problem.

```{r japan-with-cities-text, warning=FALSE, fig.width=8, fig.height=8}
ggplot() +
  geom_sf(data = japan_prefectures, fill = "#EC8E55", color = "white",
          linewidth = 0.2) +
  geom_sf(data = japan_cities_geometry, size = 3) +
  geom_sf_label(data = japan_cities_geometry, aes(label = city),
                nudge_y = 0.15) +
  coord_sf(crs = st_crs("EPSG:6668")) +
  theme_void()
```

### Nudging labels off their points

A single `nudge_y` shoves every label the same direction, which often isn't what you want — a label might end up in the sea for one city and on top of a neighbour for another. You can pass a *vector* instead, one value per city, to move each label its own direction. The order has to match the order of the rows in the data:

```{r japan-cities-nudge, warning=FALSE, fig.width=8, fig.height=8}
ggplot() +
  geom_sf(data = japan_prefectures, fill = "#EC8E55", color = "white",
          linewidth = 0.2) +
  geom_sf(data = japan_cities_geometry, size = 3) +
  geom_sf_text(data = japan_cities_geometry, aes(label = city),
               # Tokyo, Osaka, Sapporo, Fukuoka — one offset each
               nudge_x = c(-0.7, -0.7,  0.9, -0.8),
               nudge_y = c( 0.3, -0.3,  0.0, -0.3)) +
  coord_sf(crs = st_crs("EPSG:6668")) +
  theme_void()
```

That works, but hand-tuning offsets gets tedious fast and breaks the moment you add another city.

### Letting {ggrepel} do it automatically

The general solution is the [`{ggrepel}`](https://ggrepel.slowkow.com/) package, which automatically pushes labels away from their points *and* away from each other, drawing a thin leader line back to each marker. Because `ggrepel` predates `{sf}` and doesn't read geometry columns on its own, the trick is to feed it `aes(geometry = geometry)` together with `stat = "sf_coordinates"`, which extracts the point coordinates for it:

```{r japan-cities-repel, warning=FALSE, fig.width=8, fig.height=8}
library(ggrepel)

ggplot() +
  geom_sf(data = japan_prefectures, fill = "#EC8E55", color = "white",
          linewidth = 0.2) +
  geom_sf(data = japan_cities_geometry, size = 3) +
  geom_text_repel(data = japan_cities_geometry,
                  aes(label = city, geometry = geometry),
                  stat = "sf_coordinates",
                  size = 4,
                  min.segment.length = 0,  # always draw the leader line
                  box.padding = 0.3) +     # how hard to push labels apart
  coord_sf(crs = st_crs("EPSG:6668")) +
  theme_void()
```

For four well-spaced cities `ggrepel` is mild overkill, but it's exactly the tool you'll want the moment labels start colliding — add a fifth and sixth city and the manual `nudge` approach falls apart while this one keeps coping. Use `geom_label_repel()` instead of `geom_text_repel()` if you want each label in its own little box.

## Automatic geocoding by address

Using `st_as_sf()` is neat when you already have latitude and longitude, but what if you have a list of addresses instead? It's easy enough to right click on Google Maps, but you don't want to do that hundreds of times for large-scale data.

Fortunately there are online geocoding services that return GIS data for addresses you feed them. The easiest way to use them is the [`{tidygeocoder}`](https://jessecambon.github.io/tidygeocoder/) package, which connects to lots of free and paid services (run `?geo` for full details). Some common methods:

- `"osm"`: OpenStreetMap via [Nominatim](https://nominatim.org/). **FREE**, and works worldwide — including Japanese addresses.
- `"arcgis"`: [ArcGIS](https://developers.arcgis.com/). **FREE** and paid; also global.
- `"google"`: [Google](https://developers.google.com/maps/documentation/geocoding/overview). Needs an API key in `"GOOGLEGEOCODE_API_KEY"`.

::: {.callout-important}
### The US Census geocoder is US-only

The original version of this example used `method = "census"`, but the US Census service only covers the United States — it has no idea where Gakushuin University is. For Japan (or anywhere outside the US), use `"osm"` instead. This is a good habit anyway, since `"osm"` works globally.
:::

Let's make a little dataset of places around Tokyo to geocode:

Let's plot these on a map of Tokyo. We'll grab just Tokyo prefecture as a backdrop — but there's a wrinkle. Tokyo prefecture officially stretches hundreds of kilometres south to include the Izu and Ogasawara Islands, so plotting the raw prefecture leaves our three landmarks squashed into a tiny corner of a very tall, mostly-empty map. We want just the **contiguous mainland** part.

We can clip the prefecture to a sensible bounding box around the mainland using the same cookie-cutter idea as elsewhere: build a rectangle with `st_bbox()`, turn it into a polygon, and `st_intersection()` the prefecture against it. Everything outside the box (the southern islands) gets trimmed away:

```{r clip-tokyo, warning=FALSE, message=FALSE}
only_tokyo <- japan_prefectures |>
  filter(str_detect(str_to_lower(name), "tokyo|tōkyō"))

# A box around mainland Tokyo (the 23 wards + western Tama area).
# xmin/ymin = bottom-left corner, xmax/ymax = top-right, in lon/lat degrees.
tokyo_box <- st_bbox(
  c(xmin = 138.9, ymin = 35.5, xmax = 139.95, ymax = 35.95),
  crs = st_crs("EPSG:4326")
) |>
  st_as_sfc()  # turn the box into a polygon we can cut with

# Make sure both layers share a CRS before intersecting
tokyo_mainland <- only_tokyo |>
  st_transform(st_crs("EPSG:4326")) |>
  st_intersection(tokyo_box)
```

Now the backdrop is just mainland Tokyo, and our geocoded points sit comfortably across it:

```{r plot-geocoded-tokyo, warning=FALSE, fig.width=8, fig.height=6}
ggplot() +
  geom_sf(data = tokyo_mainland, fill = "#192DA1", color = "white") +
  geom_sf(data = addresses_geometry, size = 4, color = "#FF851B") +
  geom_sf_label(data = addresses_geometry, aes(label = name),
                size = 3, fill = "#FF851B", nudge_y = 0.01) +
  coord_sf(crs = st_crs("EPSG:6668")) +
  theme_void()
```

::: {.callout-note}
### Clipping vs. windowing

There are two ways to "zoom" a map, and they're not the same. `coord_sf(xlim = ..., ylim = ...)` is *windowing* — it keeps all the data but only shows part of it, like cropping a photo. `st_intersection()` is *clipping* — it actually removes the geometry outside the box, changing the underlying data. Use windowing for a quick visual zoom; use clipping when you genuinely want to drop the far-flung pieces (like Tokyo's islands) so later calculations or layers don't drag them back in.
:::

## Plotting point data from a file: universities in Tokyo

Shapefiles aren't limited to lines and areas — they can also be collections of points, and points are often what you actually want to map (every school, every station, every café). You don't have to hand-type coordinates into a `tribble()` either; lots of point data is freely available to download.

A great free source is [OpenStreetMap](https://www.openstreetmap.org/) (OSM), the "Wikipedia of maps." Everything in OSM is tagged with simple `key=value` labels — a university is tagged `amenity=university`, a café is `amenity=cafe`, a station is `railway=station`, and so on. We can ask OSM for *every* feature carrying a particular tag inside a particular area and download the result.

::: {.callout-tip}
### Want to follow along?

Below we walk through querying OSM yourself, but if you just want to follow along you can download the ready-made export here:

- [{{< fa file-code >}} `tokyo_universities.geojson`](/files/data/external_data/tokyo_universities.geojson)

Drop it into a `data` folder in your project, and you can run all the code in this section.
:::

### Querying OSM with Overpass Turbo

The tool for this is [Overpass Turbo](https://overpass-turbo.eu/), a web front-end to the OSM database. You write a short query in the **Overpass QL** language, run it, and export the matching features as a GeoJSON file — a text-based geographic format that `{sf}` reads natively.

Here's the query for every university in the Tokyo 23 special wards. Paste it into the box at [overpass-turbo.eu](https://overpass-turbo.eu/) and click **Run**:

```default
[out:json][timeout:60];
// Define the search area: Tokyo Metropolis (admin_level 4)
area["name"="東京都"]["admin_level"="4"]->.tokyo;
// Find universities of all geometry types inside that area
(
  node["amenity"="university"](area.tokyo);
  way["amenity"="university"](area.tokyo);
  relation["amenity"="university"](area.tokyo);
);
out center;
```

Let's read that line by line, because the structure is reusable for almost any OSM query:

- `[out:json][timeout:60];` — settings: return JSON, and give up after 60 seconds.
- `area["name"="東京都"]["admin_level"="4"]->.tokyo;` — find the administrative area named 東京都 (Tokyo Metropolis) and store it in a variable called `.tokyo`. `admin_level=4` is the prefecture level in Japan.
- The block in parentheses collects three things inside that area: `node`s (single points, like a small campus pinned to one spot), `way`s (buildings or campus outlines drawn as shapes), and `relation`s (complex multi-part features). A university might be tagged as any of these, so we ask for all three.
- `out center;` — output the results, and for the `way`s and `relation`s that are really shapes, return a single *centre point* instead of the full polygon. That's what keeps everything as tidy points rather than a mix of dots and blobs.

::: {.callout-tip}
### Adapting the query

Want every café in Tokyo instead? Change `amenity=university` to `amenity=cafe`. Want hospitals in Osaka? Change the area name to `大阪府` and the tag to `amenity=hospital`. The skeleton stays identical. The [OSM wiki's map features page](https://wiki.openstreetmap.org/wiki/Map_features) lists all the tags.
:::

Once it runs, click **Export → download/copy as GeoJSON** and save the file into your project as `data/tokyo_universities.geojson`.

### Reading and cleaning the data

Reading a GeoJSON is exactly like reading a shapefile — `read_sf()` handles both. As with any OSM export, some column names have colons in them (`name:en`, `name:ja`), which aren't valid R names, so we rename them to plain names right away, before any GIS step can mangle them:

```{r read-tokyo-unis-show, eval=FALSE}
tokyo_unis_raw <- read_sf("data/tokyo_universities.geojson") |>
  rename(name_en = `name:en`,
         name_ja = `name:ja`)

tokyo_unis_raw |>
  select(name, name_en, amenity)
```

```{r read-tokyo-unis, include=FALSE}
# This site stores the file under files/data/external_data/; a student following
# along would just use "data/tokyo_universities.geojson" as shown above.
tokyo_unis_raw <- read_sf(here::here("files", "data", "external_data",
                                     "tokyo_universities.geojson")) |>
  rename(name_en = `name:en`,
         name_ja = `name:ja`)
```

```{r read-tokyo-unis-output, echo=FALSE}
tokyo_unis_raw |>
  select(name, name_en, amenity)
```

There's a catch that comes up constantly with OSM data: **one university often appears as several points.** A big institution like the University of Tokyo is tagged once for its Hongō campus, once for Komaba, sometimes again for individual faculties — so a raw count badly overstates how many universities there are, and our later join would attach the same enrolment figure to each duplicate.

For a clean map we want one dot per *institution*, but OSM doesn't give us that. A single university shows up many times — separate campuses, individual faculties, even named buildings — each as its own point with a slightly different `name_en`. ### Mapping the universities

Now we map the universities the same way the Georgia schools were mapped: ward boundaries underneath, university points on top, and the `students` count mapped to the **colour** aesthetic (just like GA's `aes(color = TOTAL)`). We drop the legend so the map reads cleanly, exactly as the schools map did.

There's one tidy-up first. Our OSM query pulled universities from the whole Tokyo Metropolis, which includes the Tama-area cities to the west — but our backdrop is only the 23 special wards. Points outside the wards would float over empty space. We use the same `st_intersection()` cookie-cutter trick from before, clipping the universities to the ward boundary so we keep only the ones genuinely inside the 23 wards:

```{r clip-unis-to-wards, warning=FALSE, message=FALSE}

tokyo_wards_4326 <- tokyo_wards |>
  st_transform(st_crs("EPSG:4326"))

tokyo_unis_in_wards <- st_intersection(tokyo_wards_4326, tokyo_unis_students)

nrow(tokyo_unis_in_wards)
```

Now the map — every point sits on a ward, with student numbers driving **both** the colour and the size of each dot (and we suppress both legends to keep it clean, just like the Georgia schools map). ## Plotting other data on maps

So far we've just plotted whatever data the shapefile creators decided to include and publish in their data. But what if you want to visualize some other variable on a map? We can do this by combining our shapefile data with any other kind of data, as long as the two have a shared column. For instance, we can make a choropleth map of life expectancy with data from the World Bank.

First, let's grab some data from the World Bank for just 2022:

```{r get-wdi}
library(WDI)  # For getting data from the World Bank

indicators <- c(life_expectancy = "SP.DYN.LE00.IN")  # Life expectancy

wdi_raw <- WDI(country = "all", indicators, extra = TRUE,
               start = 2022, end = 2022)
```

Let's see what we got:

```{r head-wdi-raw}
head(wdi_raw)
```

We have a bunch of columns here, but we care about two in particular: life expectancy, and the ISO3 code. This three-letter code is a standard system for identifying countries ([see the full list here](https://en.wikipedia.org/wiki/ISO_3166-1_alpha-3)), and that column will let us combine this World Bank data with the global shapefile, which also has a column for the ISO3 code.

Let's clean up the WDI data by shrinking it down substantially so we only join the one `life_expectancy` column that we care about:

```{r clean-wdi}
wdi_clean_small <- wdi_raw |>
  select(life_expectancy, iso3c)
wdi_clean_small
```

Next we need to merge this tiny dataset into the `world_sans_antarctica` shapefile data we were using earlier. To do this we'll use a function named `left_join()`. We feed two data frames into `left_join()`, and R will keep all the rows from the first and include all the columns from both wherever the two datasets match with one specific column. We're essentially going to append the World Bank data to the end of the world shapefiles and line up rows that have matching ISO3 codes. The ISO3 column is named `iso_a3` in the shapefile data, and it's named `iso3c` in the WDI data, so we tell `left_join()` that those are the same column:

```{r combine-map-wdi}
world_map_with_life_expectancy <- world_sans_antarctica |>
  left_join(wdi_clean_small, by = c("iso_a3" = "iso3c"))
```

Now that we have a column for life expectancy, we can map it to the fill aesthetic and fill each country by 2022 life expectancy:

```{r world-life-exp, fig.width=10, fig.height=6}
ggplot() +
  geom_sf(data = world_map_with_life_expectancy,
          aes(fill = life_expectancy),
          linewidth = 0.25) +
  coord_sf(crs = st_crs("ESRI:54030")) +  # Robinson
  scale_fill_viridis_c(option = "viridis") +
  labs(fill = "Life expectancy") +
  theme_void() +
  theme(legend.position = "bottom")
```

Voila! Global life expectancy in 2022!

::: {.callout-tip}
### France and Norway

Sharp-eyed readers will notice that some countries are grayed out because they're missing data. That's because the `iso_a3` code in the Natural Earth data is coded as `-99` for some countries — historically France and Norway in particular — so the WDI data didn't merge with those rows. To fix that, we can do some manual recoding before joining in the WDI data.
:::

    name == "France" ~ "FRA",
    # Otherwise use the existing ISO3 code
    TRUE ~ iso_a3

  left_join(wdi_clean_small, by = c("iso_a3" = "iso3c"))
